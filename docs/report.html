Chain-analysis readout · every conclusion below is wrong

The transaction that lies to its analyst

Almost all Bitcoin surveillance rests on one assumption: that every input to a transaction belongs to the same person. Payjoin makes that assumption false. This is a real payjoin, settled on signet, read first the way a chain analyst would read it — and then the way it actually happened.

The heuristic

Common-input-ownership

If a transaction spends two inputs, whoever signed it had to hold the keys to both. So both inputs belong to one wallet. That inference is correct almost every time, it is cheap to compute across the whole chain, and it is the foundation the clustering step of every chain-analysis product is built on.

Payjoin breaks it by having the receiver contribute an input too. The resulting transaction is signed by two parties and looks exactly like an ordinary one-owner payment. Nothing marks it. The analyst cannot tell the difference, applies the rule, and produces a confident, wrong answer.

Findings · inferred versus true
How many people signed this transaction?
Inferred One. Both inputs were spent together, so one key-holder controlled both.
Actual Two strangers, each signing only their own input, coordinating over relays neither of them runs.
How much was actually paid?
Inferred 130,000 sat — the output that isn't change.
Actual 30,000 sat. The real figure appears in no output, in no input, and in no difference between them.
What does this tell us about the wallets involved?
Inferred Two previously separate addresses now belong to one entity. Merge their clusters and everything either has ever touched.
Actual They belong to different people. The merge is false, and it propagates — every past and future inference drawn through that link inherits the error.
Is this transaction unusual?
Inferred No. Two inputs, one payment, one change. The most ordinary shape on the chain.
Actual Correct, and that is the design. A payjoin that looked like a payjoin would flag itself; this one hides among the ordinary ones.

The obstacle

Why almost nobody can do this

Payjoin needs the receiver to add an input, so the transaction is built collaboratively. Ordinary Bitcoin needs no such handshake: you publish an address and can stay offline forever. Payjoin does — and that requirement is what has kept the most effective privacy tool Bitcoin has almost entirely undeployed.

BIP78 required the receiver to be running an HTTPS endpoint at the moment the sender paid. Workable for a merchant with a server. Impossible for a phone. BIP77 fixed the timing by adding a directory server to hold the encrypted payloads and an OHTTP relay in front of it so the directory never learns anyone's IP — solving the problem by requiring two new pieces of infrastructure, run today by a very short list of operators.

Every one of those pieces already exists, deployed and plural, as nostr relays.

What async payjoin needsBIP77 builds itNostr already has it
Store-and-forward A payjoin directory someone operates Relays — hundreds of independent operators
Payload encryption HPKE NIP-44 seal, inside a NIP-59 gift wrap
Metadata privacy An OHTTP relay someone operates A throwaway key per message

So the protocol stays BIP78 — simple, well understood, two messages — and nostr carries the waiting. No directory. No OHTTP relay. No server either party runs.

The run that produced the transaction above

The receiver was switched off

Not a simulation of being offline — the process was stopped. This is the sequence that produced txid 7d55bfd7…647a17.

earlier

The receiver prints a payjoin URI, then exits

A nostr keypair is generated for this URI alone and written to disk with the address and amount. Then the process stops. Nothing is listening.

03:25:25

The sender builds an ordinary payment and signs it

Fully valid and broadcastable. It is the fallback if the collaboration fails, and BIP78 requires it to exist before the receiver will engage — which also means a sender must commit real coins before it can probe anyone.

03:25:26

The sender publishes to three relays and gets an acknowledgement from each

The payload is gift-wrapped under a throwaway key. The intended recipient is not connected, has not been for a minute, and this works anyway.

03:26:06

The receiver is started again and finds the payload waiting

It reloads its session key from disk, reprints the identical URI, asks the relays what they are holding, and gets back the original PSBT that arrived while it was switched off.

03:26:16

The receiver checks the proposal, contributes one input, and signs

Four validations run first: that the fallback is broadcastable, that none of the sender's inputs are the receiver's own, that these inputs have not been seen before, and that the transaction actually pays the receiver. The contributed input is chosen to avoid the unnecessary-input heuristic — the wrong coin here makes a payjoin more legible than a plain payment.

seconds later

The sender validates the rewrite, signs, and broadcasts

The proposal came back altered by someone the sender has no reason to trust, so it is checked against the original before a signature is added. Across earlier failed runs this step refused every time and fell back instead — which is what it is for.

What we do not fix

What a relay can still see

A privacy claim is only worth the part of it that survives the obvious question. Relays in this run saw two kind-1059 events, each signed by a key generated for that single message, addressed to a session key used for one payjoin URI, with a randomised timestamp and sealed contents. They could not read the PSBT, the amounts, the addresses, or link either party to a persistent identity.

Open gaps, stated plainly

  • IP addresses. A relay sees the IP of whoever connects. This is exactly the leak OHTTP exists to close in BIP77, and nostr does not close it. Tor does; routing over it is not yet the default here.
  • Event size. Payload length still correlates with the number of inputs. BIP77 pads for this reason and we do not yet.
  • Fallback suitability. The receiver checks whether the fallback could be broadcast using only what Esplora exposes. A node-backed receiver would ask testmempoolaccept and get a real answer.

Reproduce it

Two terminals

Both wallets need signet coins — the receiver especially, since contributing an input is the entire mechanism, and an unfunded receiver cannot payjoin at all. 

# each side, once
cargo run -p pjn-receiver -- keygen

# terminal 1 — prints a payjoin URI, then waits
cargo run -p pjn-receiver -- serve --amount 30000

# terminal 2 — pay it
cargo run -p pjn-sender -- "bitcoin:tb1q…?amount=0.0003&pj=https://nostr.invalid/…"

Stop terminal 1 before running terminal 2, then start it again. It reprints the same URI and collects what the relays held for it.
